## 目标

### 问题与修复

持续跑图后，CPU逻辑内存逐渐接近共享预算，分区加载停止、调试数字不再更新，菜单状态虽然能改变，却不能呈现新图像。

`SectionStore`原来永久保存每个卸载坐标的修订号，且每条按4KiB保守计费。当前驻留分区数量有限，历史表却随累计路程增长。这部分属于不可驱逐的世界费用，最终会挤掉网格、后台工作及界面的空间。

现在每积累1024个近期坐标，把修订号归并到全局保守水位，再清空近期表；正常状态至多保留1023条近期记录。新安装分区的修订号严格高于适用的历史水位，防止旧异步结果在卸载、重载后被误认成新数据。归并可能保守地使其他冷加载准备失效，调用方重新准备即可；已加载分区的修订号不改动，不涉及存档或网络格式迁移。

界面原来在每次变化时重新申请整张物理像素画布，申请失败就保留旧图。客户端现在持续持有一张有计费的画布，相同尺寸和缩放时清零复用，调整尺寸时释放重建。帧开始时先尝试保护4MiB呈现余量，到绘制前释放；世界工作预检失败仍绘制界面，地形排序预算不足时使用清屏背景，继续绘制菜单与诊断信息。

## 结果

### 实际窗口验证

20261029，Windows、NVIDIA GeForce RTX 4060 Laptop GPU、Vulkan、Immediate。使用Release构建，关闭调试文字和垂直同步，帧数上限1000。设置文件可写为：

```toml
version = 2
debug = false
vsync = false
```

通过`TORSE_CLIENT_SETTINGS`指定该文件，持续跑图命令为：

```sh
cargo run --release -p torse-client -- --window --benchmark --frames 50000 --radius 4 --memory-mib 256 --benchmark-motion travel --fps-limit 1000
```

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 呈现进度 | 最后一次采样为35400帧，之后约一分钟无新增日志，进程仍运行 | 完成50000帧，保存截图时另呈现1帧 |
| 流送进度 | 未正常结束，无最终计数 | 1563次，持续推进至终点 |
| 总逻辑内存 | 另一次16000帧跑图结束时约225MiB | 采样约158～163MiB，峰值约167MiB |
| 世界逻辑内存 | 卸载记录持续累积 | 采样约3～7MiB，周期性回落 |

修复后每300帧输出`benchmark_memory total_bytes=... world_bytes=...`，与同段的`benchmark_frame`对应。下表按帧段汇总；总量包含当帧工作预留，不是进程RSS。

另用96MiB预算、半径0、暂停菜单启动600帧窗口验证：世界工作预检被拒绝，流送、重建和上传均为0，菜单仍完整呈现并正常退出。终态截图显示内存压力提示和菜单控件。该检查验证压力下的呈现路径；按键切换本身由现有输入测试覆盖，未声称这次有限帧基准执行了真人Esc操作。

```sh
cargo run --release -p torse-client -- --window --benchmark --frames 600 --radius 0 --memory-mib 96 --ui-preview pause --screenshot pressure-menu.png
```

### 回归与适用范围

全工作区与客户端GPU特性共978项测试通过，严格Clippy及Release构建通过。新增回归均隔离在测试模块中：

- 连续卸载8192个坐标，历史费用保持有界，回到曾编辑的坐标时修订号严格增加。把该回归应用到旧实现，在第2047个坐标因超过8MiB而失败。
- 通过物品操作放置方块，往返后继续切换3072个加载中心，世界预算不随路程无限增长，场景销毁后费用全部归还。
- 填满剩余世界预算后，已创建的界面画布仍能从游戏切换到暂停菜单，再切回游戏且不残留菜单像素。

本次持续跑图基准未自动编辑世界；编辑与往返场景由隔离回归覆盖。不同视距、地形复杂度、窗口尺寸与缓存热度仍会改变内存平台值。画布首次创建、调整尺寸、加载字体或新字形仍需要空间；无法满足最低启动工作集时允许明确拒绝。该修复限制历史元数据增长并避免预算不足直接跳过界面，不承诺任意小预算都能完整渲染世界，也不把操作系统分配器保留的RSS视为逻辑预算泄漏。
