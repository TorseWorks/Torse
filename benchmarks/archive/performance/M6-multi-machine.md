## 结果

### 一、真实负载

使用仓库内machine的实际Wasm构件，经正常ModRule、ExecutionHost、库存规划器、Journal和授权复制执行。没有用原生空回调替代Guest。包构建、构件编译、初始装配和恢复位于计时之外；每次事件派发仍按原规则创建新Guest实例。

新增ModLayout用于有限多机器装配，原mod_world与主程序保持默认单机器装配。同包只编译一个构件、创建一个规则；每台机器具有真实身份、进度和输入输出引用。独立模式为各机器配独立库存，共享模式使用同一对库存。输入各64件，Guest每四次唤醒转移一件，机器状态、库存和下次唤醒共同结算。

独立模式测1、16、64台，0或8个授权订阅；16和64台另测真实文件同步。共享库存测64台的冲突行为。每项分别关闭和开启现有4线程规划及组件预验证，预热5Tick后测30Tick，每种配置运行3个独立进程，交替开关顺序，共144次运行、5040行逐Tick数据，其中4320行为测量样本。

每个批次最多16条，并在批次结束后消费复制，避免默认16批队列因整Tick末才消费而失效。主表的drive只含各次drive_batch耗时，复制取出另记take_ns；为精确对照而进行的复制编码与文件保存位于计时之外，不把该表当作完整网络延迟。

运行态、事件、输出、编码帧及订阅容量均使用生产演示默认值；只把日志槽数设为主程序对应的16。内存后端最多保留128MiB日志，每订阅测试捕获最多16MiB；这是验证留存上限，不是运行态扩容。场景仍为两个加载分区，没有进行大世界或网络吞吐测量。

### 二、瓶颈与改动

64台独立机器、无订阅的内存路径中，准备均值17.004ms，规划3.211ms，编码与发布等成本更小。临时细分探针定位到运行态预算核算：每次结算都把整张事件表复制、编码、解码，少量事件变化仍重复处理全部事件。该探针不包含在正式前后测量或交付实现中。

RuntimeBudget现在按EventId和完整TimedEvent值复用已测成本，命中前比较完整内容，不能仅凭身份重用。新事件或变化内容使用真实单元素Vec编码器和解码器测量，再组合完整事件列表的编码、拥有字节与条目成本；每次仍检查总预算、事件合法性和完整运行态约束。

删除事件从缓存移除；缓存项数受事件上限限制，保留的事件拥有载荷计费不超过runtime.max_bytes。预算或CodecLimits变化时清空上下文。缓存为额外内部数据，分配器节点开销不计入逻辑载荷，不能把该计费解释为RSS。预算检查构造小状态时不再复制整张事件表。

逐任务记录直接构造Progress，避免先深复制完整RuntimeState再替换丢弃。关闭运行态优化时仍使用完整参考路径。记录布局、事件身份、提交次序、批量同步、DurableSeq门槛及恢复逻辑均保留。

容量边界验证还发现measure_inner把编码帧上限用于解码拥有字节，可能比实际decode更严格。现在只有编码受max_frame_bytes限制，解码继续使用独立OutputBudget，与正常编解码一致。新增回归覆盖编码很小、解码容器较大的输入，格式与正常解码容量未改变。

### 三、完整驱动对照

以下为关闭可选并行时的90个测量Tick，单位ms。内存后端保存完整日志，没有设备同步；文件后端执行真实追加和sync_all。

| 独立机器与订阅 | 后端 | 前P50 | 后P50 | 前P95 | 后P95 |
|---|---|---:|---:|---:|---:|
| 1台，0订阅 | 内存 | 0.147 | 0.119 | 0.242 | 0.179 |
| 16台，0订阅 | 内存 | 2.619 | 1.720 | 3.558 | 2.443 |
| 64台，0订阅 | 内存 | 22.335 | 11.026 | 25.921 | 14.244 |
| 64台，8订阅 | 内存 | 23.095 | 11.732 | 27.777 | 16.482 |
| 16台，0订阅 | 文件 | 6.943 | 6.882 | 7.990 | 7.129 |
| 64台，0订阅 | 文件 | 32.985 | 22.946 | 37.799 | 24.984 |
| 64台，8订阅 | 文件 | 34.642 | 23.556 | 39.759 | 28.094 |

64台无订阅的内存P50耗时减少约51%，文件约30%。准备均值从17.004ms降至5.912ms；文件组从17.044ms降至5.963ms。16台文件P50改善很小，刷盘波动及等待仍占主要成本，不宣称各规模都有相同比例收益。

优化后64台无订阅的文件刷盘均值11.644ms，准备5.963ms，规划3.284ms。当前文件成本主要受同步等待影响；本轮完成准备优化，没有扩大为异步持久接口改造。

开启4线程后，优化后的64台无订阅内存P50为10.849ms、文件22.950ms，与关闭模式接近。Guest回调仍串行，机器的小组件低于16KiB阈值，预验证数为0；差异视为波动，不能作为真实Guest并行收益。

共享库存场景在第4次派发发生旧值争用，只保留规范次序中的获胜机器继续唤醒，失败机器保持进度3。35Tick总派发数为286次，而独立64台为2176次；最终共享输出8件、独立输出512件。共享场景仅用于验证争用，不能用预热后只剩一台活跃机器的低耗时宣称64台持续运行性能。

### 四、验证

每种配置比较完整日志、执行快照和各订阅按ReplicaSeq排列的编码流，覆盖内存与文件、关闭与4线程、三次独立进程。优化前后72组对应产物逐字节一致。文件组均从初始检查点重放完整日志，恢复后的状态和库存相同，恢复期间Guest派发数为0。

新增真实机器回归覆盖独立及共享库存、串行和1/4线程、日志2槽对批量16的Busy，以及64台默认容量下的冻结后及已结算3项时恢复。恢复后完成当前冻结阶段不调用Guest，继续下一Tick会正常派发64次。

预算差分覆盖0、1、16、64、128个事件、嵌套字段、同身份内容变化、移除事件、精确条目和字节上下界，以及编码帧和字段限制改变。每次与完整encode/decode结果比较。客户端补充1/4线程下覆盖材质与位置色调网格的完整几何对照，已完成结果遇色调版本变化时拒绝，输入容量继续受限。

本地工作区589项、服务端mods特性117项、Mod宿主package特性18项通过，宿主另有1项原有忽略测试。并行组合专项重复10轮共370次通过，格式、默认和mods严格Clippy通过，详见[environment.txt](../data/multi-machine/environment.txt)。CI补充Windows及Linux的mods构建、严格Clippy、Mod宿主和服务端测试、真实多机器重复回归及文件基准冒烟；已有CPU取消与并行路径重复测试扩展到两个平台。远端状态查询遇GitHub API限流，新工作流尚待远端运行，不宣称远端CI通过。

### 五、复跑与结论

```sh
rustup target add wasm32-unknown-unknown
cargo test --workspace --all-targets --locked
cargo test -p torse-server --features mods --all-targets --locked
cargo test -p torse-mod-host --features package --all-targets --locked
cargo run --release -p torse-server --features mods --example multi_machine --locked -- .work/multi-machine-run --machines 64 --subscribers 8 --workers 4 --file
python apps/server/examples/multi_machine/run.py .work/multi-machine-matrix
```

输出目录必须尚不存在。矩阵脚本运行前先用上述cargo命令构建Release示例。CSV的before为5071b44加多机器装配和测量夹具，after增加事件成本复用、Progress构造和成本测量修正；三处优化源码为runtime_budget.rs、execution.rs和codec的wire.rs。各模式的配置、是否计入预热及重复序号均记录在CSV中。

当前优先事项已经取得真实规模证据并降低最大CPU成本。通用事务预验证、事件与Guest并行、投影线程和异步刷盘继续按真实需求安排，不作为本轮完成条件。本轮没有改变外围Demo的交互与表现，也没有新增媒体素材；CSV由本地运行生成。
