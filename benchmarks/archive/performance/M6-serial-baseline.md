## 目标

代码基线54c0ef8及本次串行计时改动。采用单协调器，未增加并行任务或修改提交、授权、恢复规则。

当前原生编辑负载主要耗在运行态准备、授权复制投影和同步刷盘。64项独立编辑的无存储对照中，准备占驱动总耗时约82%；8个订阅的复制投影约占72%。规划在这两项场景中均不足1%。这些比例只适用于本记录的固定负载。

### 3.2 分项成本

下表是每Tick平均耗时，单位为ms；Drive包含未单列的协调与采样成本。

| 场景 | 规划 | 准备 | 编码 | 发布 | 投影 | Flush | Drive |
|---|---|---|---|---|---|---|---|
| sink，64项，无订阅 | 0.075 | 6.975 | 0.969 | 0.375 | 0 | 0.044 | 8.478 |
| sink，128项，无订阅 | 0.158 | 25.431 | 3.061 | 1.354 | 0 | 0.123 | 30.203 |
| sink，64项，8订阅 | 0.055 | 6.775 | 0.850 | 0.414 | 20.875 | 0.008 | 29.022 |

| file，64项，无订阅 | 0.137 | 11.622 | 1.434 | 0.658 | 0 | 147.082 | 161.111 |

16、64、128项编辑每Tick分别编码52,092、669,108、2,595,668字节。128项相对64项的日志量约3.88倍，准备耗时约3.65倍。现有逐任务记录携带完整RuntimeState，任务列表反复复制、验证和编码，与这种增长相符；本次尚未进一步拆分各个内部函数的贡献。

64项编辑的2订阅与8订阅场景，投影分别为5.210ms与20.875ms，约4倍。当前每次可见提交为各订阅重新构建授权快照再做差异，订阅数与可见提交数共同放大成本。

文件后端每任务同步落盘。空Tick也有六次冻结与六次阶段结束，约24ms主要来自12次同步刷盘；64项编辑增加到76次。设备、系统缓存与同步策略影响该结果，本次不据此承诺其他设备上的延迟。

MemoryBackend的Flush随保留日志增长明显变慢，128项场景平均每Tick约1287.745ms。其逐次try_reserve_exact是需要单独评估的实现成本。sink结果已将保留日志及扩容排除，不能把memory测量直接当作无I/O的计算成本。

### 3.3 采样对照

另外顺序运行相同sink矩阵，分别开启和关闭采样，最终执行快照摘要全部相同。空Tick中位数为21.45us与17.20us，采样增加约4.25us。非空负载中位数比值在0.986到1.019之间。运行顺序和处理器频率漂移仍会影响差值，这一轮不能给出严格的采样误差界。

### 四、验证与后续

新增回归验证采样开启和关闭时日志字节、争用结果、完整执行快照与恢复一致，覆盖空Tick不投影、关闭采样、编码超限、冻结计划重试和Flush失败关闭输出门槛。记录器测试覆盖嵌套扣除、样本上限和错误返回。

工作区默认测试493项、服务端mods特性测试94项通过。工作区格式、默认Clippy及服务端mods特性Clippy均通过。CI增加小规模基准冒烟运行，检查计数、后端结果与文件恢复，不设置机器性能阈值；远端CI尚未运行。

后续优先评估RuntimeState的重复复制、校验与日志表示，以及授权投影的增量输入；持久化侧单独设计保持同步确认语义的批量屏障。规划并行仍可继续研究，本负载中的规划占比不足以解释当前主要耗时。

本次未测试真实Wasm负载、长时探索、不同世界规模、网格与GPU、网络传输、多个设备或硬件断电。没有调整事务粒度、持久确认门槛或复制可见性。

## 复现

### 二、复现与负载

在仓库根目录执行，输出目录必须尚不存在：

```sh
cargo run --release -p torse-server --example serial_baseline --locked -- --output .work/serial-baseline --ticks 30 --warmup 5
cargo run --release -p torse-server --example serial_baseline --locked -- --output .work/serial-control-on --backend sink --ticks 30 --warmup 5
cargo run --release -p torse-server --example serial_baseline --locked -- --output .work/serial-control-off --backend sink --ticks 30 --warmup 5 --unprofiled
```

每场景先执行5个预热Tick，再清空计时器，测量30个Tick，不按真实20Hz等待。世界使用两个边长16的驻留Section及两个基础容器实体，规划器只在Simulation阶段产生原生方块事务。独立编辑覆盖分区边界两侧；争用场景中每两个事务读取并修改同一格，恰好一半成功。

固定七种负载：空Tick；16、64、128项独立编辑且无订阅；64项独立编辑且有2、8个订阅；64项成对争用且有2个订阅。订阅覆盖两个分区，每次持久提交后取走完整增量，避免将慢客户端重置混入投影测量。

| 后端 | 用途与行为 |
|---|---|
| sink | 经过真实Journal编码、预留、接纳和Flush流程，丢弃输出字节；无存储持久性，仅作为计算路径对照 |
| memory | 真实MemoryBackend保留全部日志字节，同步屏障为空操作；包含现有逐次精确扩容的成本 |
| file | 真实FileJournal追加并执行File::sync_all；结束后从初始检查点重放全部日志，逐字节比较完整最终执行快照 |

三种后端共21组。每Tick断言完成N+12条记录、阶段位置、最终方块、增量批次数及持久水位。后端之间比较规范执行快照CRC32C；CRC用于结果对照，文件恢复另有完整字节比较。这里不以合成方块规划代替库存、复杂碰撞、Wasm或机器网络的性能测量。

## 边界

### 一、计时边界

计时默认关闭，通过`Server::set_serial_profiler`将同一个有界`SerialProfiler`接入执行宿主、协调器、复制源与日志。记录器只用于一条串行执行流；未来并行工作线程使用各自的记录器。数据不进入存档、规则摘要或玩法判断。

| 字段 | 包含的工作 | 扣除或排除的工作 |
|---|---|---|
| planning | collect_phase中的动作、事件和周期规划，稳定事务捕获、排序 | 冻结记录的准备、编码与发布 |
| preparation | prepare_next，包括前置校验、草稿、运行态复制、fit_state、checked_state与完整执行记录构造 | 内嵌planning |
| encoding | 日志领域载荷编码、外层记录封装、CRC和缓冲分配，同时记录封装后字节数 | 磁盘写入、队列预检查和接纳 |
| publication | 世界原子发布、执行位置、请求水位与待处理列表维护 | 内嵌projection |
| projection | 每个活动订阅的授权投影、全量比较、差异、预算检查及增量入队 | 初始基线、网络编码和传输 |
| flush | flush_through中的追加写入与同步屏障 | 结果发送、检查点和恢复 |

使用Instant测墙钟时长。嵌套子阶段的已计时长从父阶段扣除，六项之间不重复累计。准备阶段原有的运行态编码与解码验证仍归preparation，encoding仅表示日志提交编码。

tick的wall_ns还包含订阅批次取走等驱动外工作；drive_ns是各次drive_one调用时长之和。序号检查、预留、日志接纳、订阅失效通知和采样开销等形成六项之和与drive_ns之间的剩余时间。基准断言六项总和不超过drive_ns，不将剩余时间归入规划。

成功和错误返回均结束相应计时。预留受阻的重试继续复用冻结规划。样本容量事先分配，超额只增加丢弃计数，累计值继续记录；本次全部运行均无丢弃。
